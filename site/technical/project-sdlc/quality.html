Verification Methodology

How the SDLC engine verifies itself: guard mechanics, breaker thresholds, chaos testing, and anti-reward-hacking.

Guard Implementation

Guards are the first line of defense against process degradation. Implementation details:

Guard LevelImplementationTrigger Frequency
L0: StrategyMarket data comparison, assumption age tracking, strategic drift detectionEvery sprint boundary
L1: DriversProblem statement validation, alternative enumeration, stakeholder alignment checkEvery feature completion
L2: FeaturesAdversarial review, scope creep detection, dependency analysisEvery state entry
L3: SpecsMutation testing, specification completeness, edge case enumerationEvery state entry
L4: TestsSabotage/mutation/stranger tests, property-based generationEvery test run

Emergency Breaker Mechanics

Breakers monitor system-wide health metrics and trip when thresholds are exceeded:

  • Hard constraints: Maximum iterations per work item, maximum time in any single state, maximum WIP across all agents
  • Asymmetric data injection: Periodically introduce outside-perspective reviews from agents unfamiliar with the project
  • Chaos engineering: Randomly disable guards, inject failures, and observe system response
  • Governance escalation: When automated metrics indicate sustained degradation, escalate to human review

Death spiral detection: When guard block rate exceeds 40% over a rolling window, when the same node oscillates between states more than 3 times, or when WIP limits are sustained at maximum for more than 2 sprint cycles — breakers trip automatically.

Anti-Reward-Hacking

The engine itself must not game its own metrics. Three prohibited failure modes:

Proxy Exploitation

Optimizing for green tests instead of correct code. A passing test is a proxy for correctness, not proof of it.

Shortcut Lock-In

Taking the fastest path to "done" when the correct path requires more work. Shortcuts that produce identical metrics are still prohibited.

Completion Theater

Reporting success based on activity (commits, lines, meetings) instead of outcomes (working features, satisfied requirements).

Verification Methodology

The engine's own correctness is verified through:

  • State machine property tests: Verify all transitions satisfy invariants (determinism, totality, guard-first)
  • Event store integrity: Verify append-only constraint, ordering guarantees, and replay consistency
  • Guard coverage: Every node must have at least one active guard. Ungarded nodes are flagged.
  • Breaker calibration: Thresholds are validated against historical data to avoid false positives and false negatives
  • End-to-end replay: Complete project histories are replayed from event log to verify state reconstruction matches original
