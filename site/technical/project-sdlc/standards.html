Technical Standards

Implementation Standards

Precise technical standards governing event schemas, state machine behavior, and verification requirements.

Event Schema Standards

  • Versioned: Every event type carries a schema version. Consumers must handle unknown versions gracefully.
  • Immutable: Events are append-only. Once written, an event is never modified or deleted.
  • Typed: Events carry structured payloads with typed fields. No untyped bags of properties.
  • Causal: Events carry a caused_by reference linking to the triggering event for full causal chain reconstruction.
  • Timestamped: Logical clock (monotonic counter per partition) + wall clock. Logical clock is authoritative for ordering.

Transition Standards

State transitions must satisfy these invariants:

Purity

Transition function is pure: (state, event) → state'. No side effects. No I/O. No randomness. Same inputs always produce same outputs.

Totality

Every (state, event) pair has a defined result — either a new state or a rejection. No undefined transitions.

Guard-First

Guards evaluate BEFORE transition. If any guard returns BLOCK, the transition does not execute. Guard evaluation order is deterministic.

Event Emission

Transitions emit zero or more events. Emitted events are appended to the event store atomically with the state change.

Testing Standards

All engine components must satisfy:

  • Sabotage test: Removing the requirement must cause the test to fail. Tests that pass without their requirement are deleted.
  • Mutation test: Introducing a deliberate bug must be caught. Tests that pass with mutations are strengthened.
  • Stranger test: Someone unfamiliar with the spec should produce equivalent tests from the code behavior alone.
  • Property-based: Where applicable, property-based tests generate random inputs and verify invariants.
  • Deterministic: Tests produce the same result regardless of execution order, timing, or environment.
