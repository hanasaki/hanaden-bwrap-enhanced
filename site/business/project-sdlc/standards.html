Development Standards

Consistency Through Convention

Standards that ensure every contributor produces work that meets the same quality bar.

Code Standards

  • Shell scripting: POSIX-compatible where possible, Bash 4+ when required. Strict set -euo pipefail in all scripts.
  • Error handling: Every external command checked. No silent failures. Fail-fast with descriptive error messages.
  • Naming: Consistent, descriptive names. Functions prefixed by module. Variables in UPPER_SNAKE for globals, lower_snake for locals.
  • Comments: Document why, not what. Code should be self-documenting for the what.

Documentation Standards

Every Feature Must Have

  • Business driver (why it exists)
  • Technical specification (exact behavior)
  • Test coverage (automated verification)
  • Change log entry (when it shipped)

Every Spec Must Have

  • Version number and date
  • Traceability to parent feature
  • Acceptance criteria
  • Edge cases and error conditions

Process Standards

  • TDD mandatory: Every feature starts with a failing test. NOT_STARTED → GREEN is forbidden — RED must come first.
  • Review required: All changes reviewed before merge. Adversarial review encouraged.
  • Traceability required: Every commit references a spec or issue. No orphaned changes.
  • Anti-fixation active: Guards challenge assumptions at every level. "We've always done it this way" is not a justification.
