Architecture Overview

How V-Universe Works

A stakeholder-level view of the containment architecture — no kernel internals required.

The Containment Model

V-Universe creates an isolated virtual filesystem — a "universe" — where contained processes live. From inside, the process sees a complete Linux environment. From outside, the process cannot reach anything it shouldn't.

🏗

Build the Jail

The sandbox is designed and provisioned before the process starts. The process never participates in its own containment.

🔒

Lock the Door

The Linux kernel enforces boundaries. Not application code, not config files, not runtime checks — the kernel itself.

🚀

Run Inside

The process runs normally. It has access to tools, libraries, and a workspace. It just can't escape its universe.

Security Layers

Defense in depth — multiple independent layers ensure that no single failure compromises containment:

LayerMechanismWhat It Protects
MountNamespace isolationFilesystem visibility — process only sees allowed paths
UserUID/GID mappingPrivilege escalation — root inside maps to unprivileged outside
PIDProcess namespaceProcess visibility — contained processes can't see host processes
NetworkOptional network namespaceNetwork access — can be fully isolated or selectively allowed
SeccompSystem call filteringKernel surface — restricts which system calls the process can make

Virtual Filesystem

The contained process sees a carefully constructed filesystem:

  • Read-only system: /usr, /lib, /bin — bind-mounted from host, read-only
  • Private temp: /tmp, /var/tmp, /dev/shm — private tmpfs, not shared with host
  • Controlled workspace: Only explicitly listed directories are writable
  • Synthetic identity: /etc/passwd and /etc/group injected via memory file descriptors
  • No host leakage: /proc, /sys filtered; no access to host device files

Deployment Model

Single script, zero dependencies. V-Universe is one bash script that wraps bwrap (bubblewrap). No Docker daemon, no container runtime, no Kubernetes. It deploys by copying a file.

What You Need

  • Linux kernel 3.8+ (user namespaces)
  • bwrap binary (bubblewrap)
  • Standard coreutils

What You Don't Need

  • Root access
  • Daemons or services
  • Container images or registries
  • Kernel modules
