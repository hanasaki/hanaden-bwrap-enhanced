# Prompt-Block Engagement Time Measurement

## Method Overview

| Field | Value |
|---|---|
| **Method Name** | Prompt-Block Engagement Algorithm |
| **Version** | 0.0.1 |
| **Domain** | Software Engineering Metrics / Developer Productivity |
| **Purpose** | Measure actual human screen-time from timestamped interaction logs without double-billing concurrent sessions |
| **Applicable When** | Any system that produces timestamped records of human-initiated actions (prompts, commands, clicks, commits) |

---

## 1. Problem Statement

Measuring developer engagement time from interaction logs is non-trivial because:

1. **Idle gaps are invisible** -- a 2-hour gap between prompts may be lunch or may be deep reading
2. **Concurrent sessions overlap** -- if two sessions run simultaneously, wall-clock time must not be double-counted
3. **Session boundaries are unreliable** -- IDE session start/end events may not exist or may be inaccurate
4. **Reading time is unmeasured** -- the human spends time reading output after their last action

The Prompt-Block method addresses all four problems using only the timestamps of human-initiated events.

---

## 2. Core Algorithm

### 2.1 Inputs

| Input | Type | Description |
|---|---|---|
| `events[]` | Array of timestamps | All human-initiated action timestamps across ALL sessions, in ISO 8601 |
| `BLOCK_GAP` | Duration | Maximum gap between consecutive events within a continuous work block |
| `TAIL` | Duration | Reading/thinking time appended after the final event in a block |

### 2.2 Recommended Parameter Values

| Parameter | Default | Rationale |
|---|---|---|
| `BLOCK_GAP` | 30 minutes | Captures reading, thinking, and short breaks between actions. Gaps > 30 min are treated as session breaks. Adjust down for high-cadence workflows (e.g., chat), up for low-cadence (e.g., code review). |
| `TAIL` | 5 minutes | Captures reading the final system response. Adjust based on typical response length. |

### 2.3 Pseudocode

```
FUNCTION compute_engagement(events[], BLOCK_GAP, TAIL):

    INPUT:  events[] = all human-action timestamps across ALL sessions
    OUTPUT: T_engagement (total hours), blocks[] (list of [start, end] pairs)

    1. Deduplicate events by timestamp
    2. Sort events ascending by timestamp
    3. If len(events) == 0: RETURN 0, []

    4. Initialize:
         block_start = events[0]
         block_end   = events[0]
         blocks      = []

    5. For each event in events[1:]:
         IF (event - block_end) <= BLOCK_GAP:
             block_end = event              # Extend current block
         ELSE:
             blocks.append( [block_start, block_end + TAIL] )
             block_start = event            # Start new block
             block_end   = event

    6. blocks.append( [block_start, block_end + TAIL] )   # Emit final block

    7. Merge any overlapping blocks:
         Sort blocks by start
         merged = [blocks[0]]
         For each block in blocks[1:]:
             IF block.start <= merged[-1].end:
                 merged[-1].end = max(merged[-1].end, block.end)
             ELSE:
                 merged.append(block)

    8. T_engagement = SUM (block.end - block.start) for all blocks in merged

    9. RETURN T_engagement, merged
```

### 2.4 Complexity

- **Time:** O(N log N) -- dominated by the sort
- **Space:** O(N) -- for the deduplicated event list

## 3. Why This Works

### 3.1 Key Properties

| Property | How Achieved |
|---|---|
| **No double-billing** | Events from ALL sessions are merged into a single sorted timeline before blocking. Concurrent sessions share timestamps -- counted once. |
| **No fabrication** | Every event is a real, system-generated timestamp record. No inference or simulation. |
| **Idle detection** | Gaps > `BLOCK_GAP` are treated as disengagement. The human was not at the keyboard. |
| **Reading time** | `TAIL` captures the time spent reading the final system response in each block. |
| **Deterministic** | Same inputs always produce same outputs. No probabilistic modeling. |

### 3.2 What It Cannot Measure

| Limitation | Impact | Mitigation |
|---|---|---|
| **Coffee breaks < BLOCK_GAP** | Overestimates engagement | Lower `BLOCK_GAP` (increases false block-splits) |
| **Extended reading > TAIL** | Underestimates engagement | Raise `TAIL` (increases false engagement at block ends) |
| **Passive monitoring** | Human watching output without acting is invisible | Supplement with screen-time tools if needed |
| **Multi-person sessions** | Cannot distinguish which human is acting | Use per-user event attribution if available |

## 4. Derived Metrics

Once `T_engagement` is computed, the following can be derived:

### 4.1 Prompt Rate

```
R_prompt = N_events / T_engagement    (events per hour)
```

Useful for calibrating engagement intensity. Typical ranges:

| Workflow | Typical R_prompt |
|---|---|
| AI pair programming | 10-20 prompts/hr |
| Code review | 3-8 actions/hr |
| Interactive debugging | 15-30 actions/hr |

### 4.2 Engagement Density

```
D_engagement = T_engagement / T_calendar    (ratio, 0 to 1)
```

Fraction of calendar time spent actively engaged. Values > 0.5 over multi-week periods indicate intensive usage.

### 4.3 Daily Distribution

```
For each calendar date d:
    T_day(d) = SUM (block.end - block.start) for blocks overlapping date d
```

Useful for identifying peak days and ensuring no day exceeds a sanity cap (e.g., 20 hours).

## 5. Sensitivity Analysis Framework

When reporting engagement time, always provide sensitivity analysis on `BLOCK_GAP` and `TAIL`:

```
| BLOCK_GAP | TAIL  | T_engagement | Blocks | Notes                    |
|-----------|-------|--------------|--------|--------------------------|
| 15 min    | 3 min | ___          | ___    | Tight -- more block splits |
| 30 min    | 5 min | ___          | ___    | Default                  |
| 45 min    | 5 min | ___          | ___    | Loose -- fewer splits     |
| 60 min    | 10min | ___          | ___    | Very loose               |
```

If results vary > 20% across the range, report the default but flag the sensitivity.

## 6. Implementation Notes

### 6.1 Data Source Requirements

The algorithm requires only:
- A collection of timestamped human-action events
- Timestamps must be wall-clock (not relative)
- Timestamps must be system-generated (not self-reported)

Compatible sources include:
- JSONL transcript logs (filter for `type=USER_INPUT` or equivalent)
- Git commit timestamps (filter for specific author)
- IDE telemetry events
- Shell history with timestamps (`HISTTIMEFORMAT`)

### 6.2 Deduplication

If events from multiple sources are combined, deduplicate by timestamp (within a tolerance window, e.g., 1 second) to avoid inflating block density.

### 6.3 Sanity Checks

After computation, verify:
- No single day exceeds a reasonable cap (e.g., 20 hours)
- `R_prompt` falls within expected range for the workflow type
- Total blocks approximately equals expected number of work sessions
