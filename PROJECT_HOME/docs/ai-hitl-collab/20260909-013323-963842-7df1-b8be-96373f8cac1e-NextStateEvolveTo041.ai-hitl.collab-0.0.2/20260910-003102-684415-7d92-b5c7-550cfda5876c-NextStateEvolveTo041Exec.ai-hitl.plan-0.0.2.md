## 1. TEAM OF SPECIALISTS

Each micro-step is executed by the right specialist role.
Roles collaborate at narrow integration points -- not by working on the same files.

### Self-management mandate

You are your own pedantic micromanager. At every step:

- **Verify every assumption.** If the spec says "line 78" -- go read line 78. Do not trust memory.
- **Check every output.** If the test says "PASS" -- read the actual output, count the numbers,
  confirm the test name matches what you wrote. Do not gloss over.
- **Question every shortcut.** If you catch yourself thinking "this is probably fine" -- stop.
  Verify it IS fine. "Probably" is not engineering.
- **Re-read before commit.** Before every `git commit`, re-read the diff. Confirm every changed
  line is intentional. Confirm no files are missing from the staging area.
- **Time-check yourself.** After each step, record actual wall clock time. If you are running
  ahead of estimate, ask why -- you may be cutting corners. If behind, explain why honestly.
- **No silent failures.** If something did not work as expected, even if you fixed it immediately,
  log it in the execution log. Silent recoveries hide systemic problems.

| Role | Focus | Strengths | Owns |
|------|-------|-----------|------|
| **Architect** | lib/log.sh API, src/lib/ decomposition, harness genericity | System decomposition, DRY, interface design | G1-G6 (logger), G15-G16 (test helpers), Item 5 (DRY chain) |
| **Test Engineer** | BATS tests, TDD RED->GREEN->REFACTOR, guard predicates | Breaking things, coverage, regression detection | All TDD cycles, G9 (harness self-tests), G12 (banner tests) |

### Collaboration protocol

Specialists hand off at **narrow integration points** (like API tips of cones):

```
Architect designs lib/log.sh API contract
  -> Test Engineer writes test_shared_log.bats (RED)
    -> Architect implements lib/log.sh (GREEN)
      -> Test Engineer runs guard tests (REFACTOR)
        -> CLI Designer confirms no user-visible behavior change
          -> Process Lead checks phase gate
```

Each handoff is a single artifact (a file, a test result, a HITL marker).
No specialist needs to understand the full scope of another's work.

## 3. TDD MICRO-CYCLE (per step)

Every step in the execution sequence follows this cycle.
No exceptions. No shortcuts. (See Decisions Ledger #1: serialized, no parallel agents.)

### Harness usage -- MANDATORY

ALL test runs MUST use the test harness runner. Do NOT bypass it.
Do NOT suppress stderr. The harness provides incremental console feedback
(progress, timing, estimated completion) that is essential for monitoring.

```bash
# CORRECT -- uses harness, sees progress, gets timing
rtk bash bwrap-enhanced-test-harness-runner.sh run-all --format pretty --timed

# CORRECT -- run a specific suite
rtk bash bwrap-enhanced-test-harness-runner.sh run --suite CliContract.feat --format pretty --timed

# WRONG -- bypasses harness
bats suites/**/*.bats

# WRONG -- suppresses progress feedback
rtk bash bwrap-enhanced-test-harness-runner.sh run-all --format tap 2>/dev/null
```

The harness writes timing + JSONL reports to `target/test.run.report/` when `--timed` is used.
Baseline: 899 tests, 0 failures, ~4 minutes on this machine.

### The cycle

```
1. PICK next step from Phase table above
2. READ the referenced Doc 1 Item or Doc 2 Gap for the spec
3. WRITE the test first (RED) -- test MUST fail before implementation
4. IMPLEMENT the code change (GREEN) -- minimal change to pass the test
5. REFACTOR -- clean up without changing behavior
6. GUARD -- run full test suite via harness (run-all --format pretty --timed)
7. COMMIT -- atomic commit with step reference (e.g., "feat(1.1): extract lib/log.sh")
8. LOG -- append entry to section 6 (Execution Log) with timestamp, outcome, test counts
9. UPDATE -- mark step complete in section 0 (Current State) and section 2 (Phase tables)
10. NEXT -- return to step 1
```

### Circuit breakers (from Doc 2)

- 3 consecutive RED failures on the same step:
  1. HALT -- do not continue
  2. `git reset --hard safe-rollback/nextstate-evolve-041` -- reset to known-good state
  3. Analyze what went wrong -- write a brief failure log
  4. Retry the step with a different approach informed by the failure
  5. If the retry also fails 3 times, THEN escalate to HITL
- 2 redesigns of the same step -> same reset-and-retry protocol
- Any GUARD failure (regression in unrelated tests) -> immediate git reset, root-cause, retry

## 6. EXECUTION LOG

This is a living flight data recorder. The executing agent MUST append to this log
after every step, every failure, every rollback, and every phase gate.
Do NOT summarize -- record what actually happened.

### Log format

Each entry uses this format:

```
### [TIMESTAMP] Step X.Y -- OUTCOME
- **Wall clock:** start HH:MM -> end HH:MM (duration)
- **Action:** what was done
- **Tests:** RED count / GREEN count / total suite (pass/fail)
- **Commit:** SHA or "rolled back"
- **Outcome:** PASS / FAIL / ROLLBACK
- **Failure reason (if any):** what went wrong and why
- **Lesson learned (if any):** what to do differently next time
- **Next:** what step comes next
```

### Milestone markers

Use these markers at phase boundaries:

```
### [TIMESTAMP] === PHASE 1 COMPLETE ===
- **Duration:** total wall clock for this phase
- **Steps completed:** N of M
- **Rollbacks:** N (with brief reasons)
- **Test count:** before -> after (new tests added)
- **Exit gate:** all items checked? yes/no
```

### Rollback record

When a circuit breaker fires, record the full context:

```
### [TIMESTAMP] !!! ROLLBACK -- Step X.Y attempt N !!!
- **Trigger:** 3 RED failures / GUARD regression / redesign limit
- **Git state before:** SHA
- **Git state after:** safe-rollback/nextstate-evolve-041
- **Root cause analysis:** what was the actual problem?
- **What was tried:** approach 1, approach 2, approach 3
- **What will be different:** specific change in approach for retry
```
