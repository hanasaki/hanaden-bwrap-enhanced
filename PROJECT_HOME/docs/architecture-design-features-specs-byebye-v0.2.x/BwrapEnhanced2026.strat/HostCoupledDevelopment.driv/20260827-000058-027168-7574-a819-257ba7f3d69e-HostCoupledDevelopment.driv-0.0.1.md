# HostCoupledDevelopment: Workstation Path Lock-In — Technical Driver

## Problem Statement

A project that embeds host-specific filesystem paths as hardcoded literals in
its source, tests, or documentation is not a portable artifact — it is a
snapshot of one workstation's layout. This deficit does not require an adversary
or an unusual deployment scenario to manifest; it appears the moment a second
developer, a CI runner, or a disaster-recovery clone attempts to use the project.

**What "host-specific path" means in this project's context:**

- Absolute NFS paths such as `/homes/home-local/hanasaki/...` or
  `/homes/home-remote/home-remote-nfs/...` that are specific to a single
  server's autofs topology.
- Absolute workstation paths such as `/home/hanasaki/...` that encode a
  particular user account name.
- Hardcoded tool installation paths such as `/homes/home-local/hanasaki/.local/bin/mise`
  instead of resolving via `$MISE_BIN` or `which mise`.

**Why this constitutes a persistent, non-negotiable deficit (not merely a preference):**

The project exists to provision and test a security sandbox. That sandbox must
be provably reproducible — its behavior must not differ across machines, users,
or time. If the test suite that verifies the sandbox hardcodes the paths of the
machine that ran the tests, the tests do not verify the sandbox; they verify
one specific host layout. The correctness claim collapses.

Additionally, the deficit is self-concealing: hardcoded paths that happen to
exist on the development workstation produce passing tests. The broken state
only becomes visible on a different machine, by which point the coupling may
have accumulated across dozens of files with no automated detection.

There is no alert, lint rule, or CI gate that catches a newly introduced
hardcoded path. Regressions accumulate silently.

## Technical Impact

| Impact Dimension | Current State (Coupled) | Target State (Portable) | Delta |
|:---|:---|:---|:---|
| **Machine portability** | Project unusable on any machine without identical NFS topology and user account name | Project clones and runs on any POSIX machine with bwrap and bash | Zero portability → Full portability |
| **CI/CD enablement** | Automated test runners cannot execute; all tests require the specific workstation | Tests pass on any ephemeral CI runner (GitHub Actions, Forgejo, Woodpecker) | Blocked → Fully enabled |
| **Collaboration surface** | No second developer can contribute, reproduce bugs, or run tests | Any developer with project checkout can run the full test suite | 1 person → N contributors |
| **Disaster recovery** | Losing the workstation means losing the ability to run, validate, or reproduce the project | Project is self-contained; recoverable from any git clone | Single point of failure → Eliminated |
| **Regression detection** | New host-specific paths silently pass tests on author's machine | Automated portability enforcement test catches any new absolute path literal | Silent accumulation → Immediate CI failure |
| **Spec document accuracy** | Spec docs describe host filesystem layout, not sandbox behavior | Spec docs describe only sandbox-internal paths and behaviors | Host-coupled descriptions → Sandbox-accurate |

## Constraints

- The portability enforcement mechanism must not require modifying the kernel,
  installing system-wide linters, or adding CI-only dependencies not present in
  the development environment.
- The mechanism must detect violations at commit time (pre-commit hook or test
  suite gate), not only in CI, so the feedback loop is immediate.
- Path resolution must use environment variables (`$PROJECT_HOME`, `$MISE_BIN`,
  `$HOST_HOME`) already established by the project's boot conventions — it must
  not introduce a new configuration layer.
- Spec documents that legitimately reference sandbox-internal paths (e.g.,
  `/homes` within the bwrap namespace) must be distinguishable from documents
  that hardcode host-external paths; the enforcement rule must handle both cases.
- The fix must not alter the observable behavior of any currently passing test.
