# Kanban Ordering & Dependency Resolution — Brainstorming

> **Status:** DRAFT — Deferred for future work
> **Origin:** Conversation `fea4df1b-8758-420d-af0f-c59bdabb3af1`, 2026-09-06
> **Trigger:** User question: "how do we populate the kanban board using the
>   sdlc process and list/fix them in the right order... kanban has no ordering...
>   need ordering auto figured out like maven and pom.xml do but with our specs"

---

## Part 1: The Problem Statement

Kanban is a pull-based flow system with WIP limits. It deliberately avoids
pre-ordering because the *pull signal* from downstream IS the ordering mechanism
(Toyota Production System). However, this project is not a factory with
steady-state flow — it has a *finite dependency graph* of spec-driven work items
where ordering matters for correctness (you can't implement `stop` before
`start` has PID tracking).

**Core question:** How do items get ordered when they enter the kanban board
from the spec tree?

---

## Part 2: Industry Survey

| System | How It Gets Ordering | Mechanism |
|:-------|:--------------------|:----------|
| **Maven/POM** | `<dependencies>` in `pom.xml` → DAG → toposort → build order | Declarative edges in structured data |
| **Gradle** | `dependencies { }` block → task graph → topological execution | Same — DAG + toposort |
| **Make** | Target prerequisites → DAG → toposort | `target: prereq1 prereq2` |
| **Nix/Guix** | Derivation inputs → DAG → build plan | Functional dependency closures |
| **Terraform** | `depends_on` + reference graph → plan → apply order | Implicit + explicit edges |
| **Scrum** | Sprint backlog ordering by PO → manual priority | Human ordering, no DAG |
| **Kanban (Toyota)** | WIP limits + pull + class of service → emergent order | No explicit ordering — by design |
| **SAFe PI Planning** | Feature dependencies → program board → string art | Visual dependency mapping |
| **Our SDLC Engine** | `dependencies: list[work_item_id]` + live `priority_score` | Specified in v0.0.6 §14.5 |

**Industry conclusion:** Use kanban for flow management (WIP limits, pull,
cycle time) but overlay a DAG for sequencing. That's what SAFe's program board
does, what Azure DevOps "predecessor" links do, and what our SDLC engine's
`dependencies` field was designed to do.

## Part 3: Gap Analysis of SdlcEngineSpec v0.0.6 `dependencies + priority_score`

### What the Spec Actually Says

**IWorkItem.dependencies** — §14.5, L1542:
```
| `dependencies` | `list[work_item_id]` | Must be DONE before READY |
```

**State machine** — §7.2, L970 (mermaid):
```
BL -->|deps DONE, live score| RD["ready\npullable, no owner"]
```
Guard condition: the `backlog → ready` transition fires only when all items in
`dependencies[]` are `DONE`.

**Machine JSON** — catalog.machine.json, L19-27:
```json
"backlog": {
  "on": {
    "WORK_CREATED": { "target": "backlog" },
    "WORK_DECOMPOSED": { "target": "backlog" },
    "WORK_UNBLOCKED": { "target": "ready" }
  }
}
```
Only `WORK_UNBLOCKED` transitions `backlog → ready`.

**DAG walk** — §7.1, L946:
```
| DAG | Parallelism = width. On `MERGE_ACCEPTED`, walk and `WORK_UNBLOCKED`. |
```
Cascade: when item A finishes (`MERGE_ACCEPTED`), the hub walks the DAG to find
items depending on A. For each one where all deps are now `DONE`, hub emits
`WORK_UNBLOCKED`.

**priority_score** — §20.1, L2222:
```
priority_score(card) =
    w_p0    * is_P0
  + w_dep   * dependents_blocked_count
  + w_age   * age_in_ready_ms
  + w_merge * merge_point_waiting_on_this
  + w_risk  * security_or_breaker_flag
  + w_zoom  * (1 / (1 + nesting_level))
  - w_wip   * (column_wip / column_wip_limit)
  - w_lease * already_has_owner
```

**Pull query** — §20.2, L2238:
```sql
SELECT filename_id FROM card
 WHERE column = 'ready'
   AND owner_agent IS NULL
   AND capabilities_match(agent)
   AND subtree_free(owned_subtree)
   AND wip_ok(agent, column)
 ORDER BY score DESC, entered_column_ts ASC
 LIMIT 1
```

### What It DOES Solve

| Problem | How It's Solved |
|:--------|:----------------|
| "What can I work on now?" | `dependencies` gate: only items with all deps `DONE` are `ready` |
| "Which ready item is most important?" | `priority_score` — live-ranked, highest wins |
| "When a task finishes, what gets unblocked?" | DAG walk on `MERGE_ACCEPTED` → `WORK_UNBLOCKED` cascade |
| "Can two things run in parallel?" | DAG width = parallelism. Independent branches have no dependency edges |
| "How do I avoid working on something too early?" | `backlog` is not pullable. Only `WORK_UNBLOCKED` makes it `ready` |

**This IS a topological sort — just spread across time.** Instead of computing
the full order up-front (like Maven does), it computes the *next available layer*
on every `MERGE_ACCEPTED`. The effect is the same: you never work on something
whose prerequisites aren't done.

### 5 Specific Gaps Found

**Gap 1: No dependency-edge producer**

The spec defines how to *consume* dependency edges (DAG walk + `WORK_UNBLOCKED`)
but not how to *produce* them. The `WORK_CREATED` event payload at L1255 is
`(work_item_id, node_ref, column=backlog)` — no `dependencies` list in the
payload. Who populates `dependencies[]`? Human? Auto-inferred from tree?
`WORK_DECOMPOSED` propagation?

> This is the core missing piece. It's like Maven having the reactor build order
> algorithm but no `<dependency>` XML element.

**Gap 2: No dependency table in DB schema**

§18.3 Kanban Projector schema defines `CREATE TABLE card(...)` but has no
`dependencies` column and no `card_dependency` join table. The
`IWorkItem.dependencies: list[work_item_id]` trait field has no storage
counterpart. Only `parent_card TEXT` exists (vertical hierarchy only).

**Gap 3: Zero-dependency bootstrap problem**

If a card has `dependencies: []` (empty list), who emits the `WORK_UNBLOCKED`
to transition it from `backlog → ready`? The machine.json says `WORK_CREATED`
loops back to `backlog`. `WORK_UNBLOCKED` is the only exit. But
`WORK_UNBLOCKED` is emitted by the DAG walk on `MERGE_ACCEPTED`. If a card has
no dependencies, no `MERGE_ACCEPTED` will ever walk to it.

The walkthrough at L2193 sidesteps this — it shows `WORK_CREATED dependents
ready` going directly to ready, contradicting the machine.json.

**Gap 4: ID space mismatch**

`dependencies` type is `list[work_item_id]`. Work items are runtime cards. Spec
files have `filename-id`s. There's a conceptual gap between:
- Spec-level dependencies (static, design time: "StopSubcommand needs PidTracking")
- Work-item dependencies (dynamic, execution time: "card-X needs card-Y DONE")

Maven solves this by making the artifact identifier the same in both declaration
and build plan. This system has two different ID spaces.

**Gap 5: No up-front plan view**

The mechanism is reactive (event-driven cascade), not batch (pre-computed plan).
It answers "what's unblocked NOW?" but not "what's the full build order?" Maven
computes the full reactor order up-front before building anything.

### Verdict

`dependencies + priority_score` IS a valid runtime ordering mechanism for the
future Rust engine. It is NOT available today (the engine doesn't exist), and
it has 5 gaps in the spec itself that would need resolution before implementation.

| # | Gap | Impact | Fix Difficulty |
|:--|:----|:-------|:---------------|
| 1 | No dep-edge producer | Can't build DAG without edges | Medium — add `depends-on:` to spec frontmatter |
| 2 | No dep storage | Engine can't persist/query deps | Small — add `card_dependency` join table |
| 3 | Zero-dep bootstrap | Items with no deps stuck in backlog | Small — add "immediate WORK_UNBLOCKED for empty deps" |
| 4 | ID space mismatch | Specs can't ref each other at design time | Medium — allow `filename-id` as dep targets |
| 5 | No up-front plan | Can't preview full execution order | Design decision |

### Open Question (deferred)

Are these spec defects or intentional deferrals? Gaps 1 and 3 look like genuine
omissions. Gaps 2, 4, 5 could be implementation details intentionally left to
the implementer. Requires human review of the `ai-lock: FATAL` SDLC engine spec.

## Part 4: Proposed Resolution Approaches (for future work)

### Option A: Add `depends-on:` to spec YAML frontmatter

Each spec `.md` file gets a `depends-on: [list of filename-ids]` field. A
shell/Python script walks the spec tree, reads frontmatter, builds a DAG,
toposorts, and emits ordered kanban cards.

**Pros:** Pure data, Maven-like, scripts can validate for cycles
**Cons:** Manual maintenance (same as pom.xml)

### Option B: Infer ordering from tree hierarchy alone

Bottom-up: all leaf SPECs with `tdd.state: NOT_STARTED` → READY. Parent
FEAT/ARCH → READY only when all child SPECs are PASS. No cross-cutting edges.

**Pros:** Zero manual edge maintenance, pure convention
**Cons:** Can't express "stop depends on PID tracking" (sibling deps)

### Option C: Hybrid A+B (recommended)

Tree hierarchy for vertical deps (automatic) + `depends-on:` for horizontal
cross-cutting deps (explicit). Script toposorts both.

### Option D: Full SDLC engine implementation

Implement the Rust engine with all traits. End-state but impractical today.

code bug.
